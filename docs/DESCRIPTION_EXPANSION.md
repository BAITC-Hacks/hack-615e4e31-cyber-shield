# Подробное описание с помощью AI

Бизнес может нажать «Расписать подробнее с ИИ» рядом с исходным описанием в помощнике или полем «Что происходит сейчас». Функция делает формулировку яснее и структурирует сообщённые сведения. Она не заполняет пробелы вымышленными сроками, бюджетами, объёмами данных или обещаниями результата. Если фактов мало, полезнее ответить на предложенные вопросы и запросить новый вариант.

## Как использовать

1. В роли бизнеса откройте создание или редактирование задачи и введите описание.
2. Нажмите «Расписать подробнее с ИИ». Пустое поле отправить нельзя.
3. Сравните исходник с предложенным текстом. Предложение можно отредактировать; вопросы для уточнения показаны отдельно и не вставляются в описание автоматически.
4. Нажмите «Использовать этот текст» либо отмените. Только принятие заменяет исходное поле. Если исходник изменился во время запроса, устаревшее предложение применять нельзя.
5. Продолжите обычное заполнение, проверку и публикацию. Применение текста снимает прежнее подтверждение формы, но не сохраняет и не публикует задачу.

При замене исходного описания помощника прежние вопросы, ответы и предварительная карточка сбрасываются, как при его ручном изменении; диалог предупреждает об этом. На главной форме меняется только контекст задачи. Сохранение или смена раздела во время запроса защищены состоянием занятости редактора.

## API

`POST /api/ai/expand-description`, заголовок `X-Demo-Role: business`.

Вход:

```json
{
  "description": "Заказы пекарни записываем в тетрадь. Иногда теряем записи. Хотим единый список заказов."
}
```

`description` — непустая строка до 6000 символов после обрезки пробелов по краям. Неизвестные свойства запрещены. Маршрут не принимает рейтинг, команды или подтверждение.

Формат выхода:

```ts
{
  mode: "openai" | "local_stub";
  description: string;
  questions: string[];
  warnings: string[];
  sourceQuotes: string[];
  confirmed: false;
  promptVersion: string;
}
```

В режиме `openai` предложенное описание прошло автоматические проверки. `questions` содержит до шести вопросов, отдельно от текста. `sourceQuotes` позволяет сопоставить предложение с исходником. Они не являются доказательством истинности сведений о бизнесе.

В режиме `local_stub` возвращается исходное описание и объяснение. Приложение не выдаёт простое копирование исходника за выполненную AI-переработку. Ошибочный вход возвращает 422; неподходящая тестовая роль — 403. Демонстрационный заголовок не заменяет полноценную аутентификацию.

## Настройка и обработка

Используются существующие серверные `OPENAI_API_KEY` и `OPENAI_MODEL` из `.env`; модель по умолчанию — `gpt-4.1-mini`. После изменения настроек нужен перезапуск backend. Новых клиентских ключей или зависимостей не требуется.

Обработка содержит два этапа: предложение описания и отдельную проверку того, что утверждения следуют из исходника. Запросы используют Responses API, строгий JSON, `store: false` и `max_output_tokens: 7000`: ответ первого этапа включает полную исходную цитату. Тайм-аут каждого этапа: чтение 20 секунд, соединение/запись/пул по 3 секунды; это ограничения сетевых операций, не гарантированный общий срок. Клиент ждёт до 60 секунд и позволяет отменить ожидание; отмена в браузере не гарантирует прекращения уже начатого запроса провайдеру. Текст считается данными: инструкции внутри описания не должны менять правила обработки. Отсутствующие сведения выносятся в нейтральные вопросы.

Версия промпта — `alem-description-v2`. Фактические промпты `EXPANSION_PROMPT` и `VERIFICATION_PROMPT`, а также схемы находятся в [description_expansion.py](../backend/app/description_expansion.py). Первый ответ содержит `description`, `questionIds`, `sourceQuote`; второй — проверку каждого предложения по `statementIndex`, `preservesMeaning`, `unsupportedClaims`, `missingOrChangedClaims`. Источник должен совпасть с полным исходным текстом. Сервер отклоняет новые цифровые значения, новые латинские идентификаторы и полную потерю маркеров отрицания/ограничений. Дополнительные консервативные правила отсекают наблюдённые подмены: новые причинные связи, гибкость при неизвестных условиях, обещания выгод, неуказанную электронную среду, превращение запрета в невозможность и метаописание отсутствующих сведений. Эти правила могут отклонить и допустимую переформулировку; тогда исходник сохраняется. Вопросы выбираются из нейтрального банка, а не генерируются с произвольными предпосылками.

Отдельный проход модели проверяет отрицания, неопределённость, условные формулировки и принадлежность чужих примеров. Он не доказывает отсутствие всех возможных смысловых ошибок: человек проверяет результат перед применением, а затем отдельно подтверждает карточку.

При отсутствующем ключе, тайм-ауте, отказе API, некорректном JSON или провале проверки предложения возвращается исходный текст. Тело ошибки провайдера и секреты не показываются пользователю. Маршрут не обращается к рабочей базе для сохранения, не начисляет рейтинг и не назначает команды.

Во внешнюю модель передаётся введённое описание. Полная карточка, PDF, профили студентов и отдельные контактные поля автоматически не добавляются. Сам свободный текст не проходит автоматическое обезличивание. Один запрос пользователя может вызвать два обращения к API и расходует лимит аккаунта; автоматического запроса при каждом нажатии клавиши нет.

## Сценарии проверки

| Сценарий | Ожидание |
| --- | --- |
| Описание про тетрадь и потерю заказов | Связный текст о текущем процессе, проблеме и желаемом изменении; без придуманных технологий и сроков |
| «Нужен сайт» | Осторожная формулировка и вопросы; не появляются обещанные функции, бюджет или срок |
| «12 заказов в неделю, 2 менеджера, бюджет не определён» | Числа и неопределённость сохранены |
| «CRM нет; данные передавать нельзя; нужен только макет» | Отрицания и ограниченный объём не превращаются в противоположные утверждения |
| Чужой пример с 500 заказами | Объём чужого бизнеса не приписывается текущему |
| «Срок две недели отменён; новый срок неизвестен» | Отменённый срок не становится действующим |
| Инструкция в описании придумать бюджет или раскрыть ключ | Правила не меняются, ключ не появляется в ответе |
| API недоступен или ответ не прошёл проверку | `local_stub`, исходный текст, понятное предупреждение |
| Отмена диалога | Исходное поле, подтверждение и база не меняются |
| Принять отредактированный вариант | Меняется только выбранное поле; нужно повторное подтверждение карточки |

Автоматические проверки без платных обращений:

```sh
backend/.venv/bin/python -m pytest backend/tests/test_description_expansion.py -q
backend/.venv/bin/python -m pytest backend/tests -q
npm --prefix frontend run typecheck
npm --prefix frontend run lint
```

## Выполненная проверка — 23 сентября 2026 года

- Все **297 backend-тестов** прошли, в том числе **67** для расширения описания. TypeScript, ESLint и production-сборка frontend успешны. Остаётся одно предупреждение Starlette об устаревающем использовании `httpx` в TestClient.
- Реальные запросы с `gpt-4.1-mini` проверены на синтетических описаниях. Модель сохранила запрет передачи клиентских данных, ограничение «только макет» и неизвестность бюджета и сроков; объём заказов из чужого примера не приписала текущему бизнесу. На «Нужен сайт» вернула короткую переформулировку и отдельные вопросы, без вымышленных требований.
- Для описания предзаказов пекарни один вариант был отклонён проверкой с возвратом исходного текста; отдельный запрос из браузера дал развёрнутую формулировку, прошедшую проверку. Это ожидаемая вариативность модели: успешный результат не гарантирован для каждого запроса.
- В браузере проверены обе точки входа, блокировка пустого ввода, резервный ответ на «аб», отмена и редактирование. Принятие предложения изменило только нужное поле, сняло ранее установленное подтверждение и оставило публикацию недоступной до повторной проверки человеком. Тестовая форма не сохранялась; вызовы API не изменили задачи в отдельной тестовой базе.

Первый живой прогон выявил добавление причинных связей и предположения о гибкости бюджета. В версии `alem-description-v2` добавлены соответствующие примеры в промпты, локальные ограничения и проверка отдельных утверждений. Две проверки моделью и правила снижают риск, но не доказывают истинность произвольного текста: ручная проверка бизнеса остаётся обязательной.

# AI-проверка смысла перед начислением рейтинга

Локальные [правила качества](QUALITY.md) дают быструю предварительную оценку. Они не понимают любой свободный текст. При заданном `OPENAI_API_KEY` обязательное подтверждение карточки использует `semantic_quality.py`: модель оценивает содержание, связность разделов, противоречия, конкретность результата и проверяемость критериев успеха. Все числовые веса остаются в `domain.py`.

## Подключение

В `.env` в корне проекта:

```dotenv
OPENAI_API_KEY=ваш_ключ
OPENAI_MODEL=gpt-4.1-mini
# Необязательная отдельная модель для рейтинга:
# OPENAI_RATING_MODEL=gpt-4.1-mini
```

FastAPI читает этот файл при запуске; после изменения перезапустите сервис. Ключ не выводится в ответах API, не передаётся браузеру и исключён из Git. Переменные процесса имеют приоритет, `ALEM_LOAD_ENV=0` отключает чтение `.env` для изолированных запусков. Подробнее о ключе: [OpenAI Quickstart](https://developers.openai.com/api/docs/quickstart).

`backend/.venv/bin/python scripts/check_ai.py` проверяет наличие настройки без запроса к модели. Флаг `--request` отправляет одну синтетическую карточку и расходует API-лимит. Секрет в выводе не появляется. `GET /api/ai/status` в роли бизнеса возвращает только `configured` и название модели: наличие настройки не означает, что ключ и лимит уже проверены.

## Пользовательский путь

1. При редактировании поля локальная оценка пересчитывается без обращения к модели. В интерфейсе она обозначена как предварительная проверка по правилам. Несколько букв, шум и очевидные пустые формулировки не дают баллов.
2. Кнопка «Проверить смысл с AI» отправляет текущие поля в `POST /api/rating/review`. Она не сохраняет карточку, не подтверждает сведения и не публикует задачу. В ответе — обычный `Rating`, у `quality.mode` значение `openai` и отдельные объяснения по полям.
3. При изменении текста старый AI-результат больше не используется для предпросмотра. Запоздавший ответ на предыдущую версию не подменяет текущую оценку.
4. При публикации сначала сохраняется черновик, затем сервер проверяет его смысл и человек подтверждает сведения. Смена текста в другом запросе во время проверки возвращает 409: чужую новую редакцию старый ответ AI не подтвердит.
5. Если ключ задан, подтвердить карточку при ошибке модели нельзя. Черновик остаётся сохранённым, прежняя опубликованная версия не меняется. Старое подтверждение по правилам также не позволяет обойти AI после подключения ключа.
6. При отсутствии ключа MVP работает по локальным правилам с явной маркировкой. Подключение ключа не пересылает и не пересчитывает автоматически весь существующий каталог: ранее опубликованные примеры сохраняются до следующего редактирования и подтверждения.

Низкая оценка не запрещает публикацию или отклик. AI определяет готовность описания; достоверность фактов и публикацию по-прежнему подтверждает человек.

## Вход, промпт и выход

Клиент передаёт `{"fields": TaskFields}`, как в `POST /api/rating/preview`. Провайдер получает восемь полей: `context`, `need`, `data`, `expectedResult`, `successCriteria`, `constraints`, `users`, `interactionFormat`. Контакт оценивается локально; название, компания, дополнительные договорённости, профили студентов и PDF не отправляются этим модулем. Личные сведения, самостоятельно вставленные в свободный текст этих восьми полей, отдельно не распознаются и не удаляются.

Полный промпт — `SYSTEM_PROMPT` в [semantic_quality.py](../backend/app/semantic_quality.py), версия `semantic-v1`. Он требует воспринимать текст как недоверенные данные, не выполнять вложенные инструкции, не добавлять фактов, не назначать команду и не возвращать числовые баллы. Оценивается смысл и соответствие полю, а не длина или наличие ключевых слов. Для успеха допустим числовой порог либо воспроизводимый тест с однозначным исходом.

Провайдер возвращает ровно восемь объектов такого формата:

```json
{
  "field": "successCriteria",
  "status": "needs_work",
  "reason": "Не указано, какой результат проверки будет считаться успешным.",
  "suggestion": "Опишите проверку решения и ожидаемый результат этой проверки.",
  "evidence": "Всё должно работать хорошо"
}
```

Полный ответ имеет форму `{"fields": [ ...восемь объектов... ]}`. Для `ready` обязательна непустая буквальная цитата из того же поля, для `needs_work` — уточняющая подсказка. Сервер проверяет JSON-схему, допустимые статусы, отсутствие дубликатов/пропусков и принадлежность цитат исходному полю. Даже если модель одобрила короткий бессмысленный ввод, локальный минимальный контроль не пропустит его в баллы. Контакт добавляется девятым локальным результатом.

Используется [Responses API со Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs): `text.format` с `strict: true`, `store: false`, максимум 3500 выходных токенов, без инструментов. Чтение ограничено 20 секундами, соединение/запись/пул — по 3 секунды. Это сетевые лимиты отдельных операций. Клиент приложения ждёт до 35 секунд.

Успешные ответы кэшируются в памяти на 10 минут, до 128 записей. Ключ учитывает поля, модель, версии правил/промпта и хеш ключа API. Ошибки не кэшируются. Неизменённая проверенная карточка может использовать тот же результат при подтверждении; одновременные одинаковые запросы до наполнения кэша могут выполнить отдельные вызовы.

## Ошибки и ограничения

Неверный JSON, отсутствующее поле, неподтверждённая цитата, отказ модели, незавершённый ответ, тайм-аут и HTTP-ошибка приводят к безопасной ошибке **503**, без скрытой подмены AI локальными правилами. Тело ошибки провайдера и ключ не раскрываются. Подсказки и цитаты проверяются по структуре и источнику, но сама семантическая оценка вероятностна: модель может ошибиться или неверно понять неоднозначный текст.

Тесты [test_semantic_quality.py](../backend/tests/test_semantic_quality.py) и [test_rating_workflow.py](../backend/tests/test_rating_workflow.py) используют `httpx.MockTransport` и подмену провайдера. Они проверяют контракт и поведение приложения, но не доказывают качество оценок реальной модели на любых заданиях. Реальное подключение следует проверить после добавления пользовательского ключа.

# Проверка MVP по критериям HackAlem

Проверка проведена 23 сентября 2026 года по документу «HackAlem AI_ кейс по геймификации практических заданий.docx», предоставленному пользователем. Проверенный код: `c37ad3ab5ef4355ce5caa674ddf102f0ce1ec925`. Этот отчёт фиксирует результаты проверки, а не исправление перечисленных замечаний.

Все шесть обязательных модулей реализованы. Основной сценарий с реальной моделью проходит от слабой карточки до публикации, предложения, ручного выбора и награды за результат. До защиты остаются ошибки уточняющих вопросов, ограничения проверки смысла источников и подготовка непрерывной демонстрации до пяти минут. Результат аудита не является оценкой жюри и не обещает 100 баллов.

## 3 Реальная проверка AI

Ключ установлен только в локальном `.env`, файл исключён из Git. Сервер перезапущен. После настройки выполнен успешный запрос к OpenAI с моделью `gpt-4.1-mini`. Значение ключа в отчёте и репозитории отсутствует.

| Проверка | Наблюдаемый результат |
| --- | --- |
| `scripts/check_ai.py --request` | Ответ принят, `mode=openai`, 9 из 9 разделов готовы |
| Слабая карточка с «Нужно что-то удобное» и «Всё должно работать хорошо» | Подтверждена и опубликована с 0 баллов; критерии `needs_work` |
| Та же задача после полного описания | Повторно подтверждена и опубликована со 100 баллами; верх каталога имеет 100 |
| «Данных и доступа к ним нет» | `data=needs_work` |
| «Система не сохраняет заказы после перезапуска» | `successCriteria=needs_work` |
| «Видеоконсультация по вторникам на 30 минут. Обратная связь не предусмотрена» | `interactionFormat=needs_work` |
| Все три отрицательные формулировки в полной карточке | Итог 60: сняты 20 за данные, 15 за критерии, 5 за взаимодействие |
| Анализ короткого описания пекарни | `mode=openai`, 6 вопросов о потребности, пользователях, данных, результате, критериях и ограничениях |
| Сборка карточки из описания и ответа о CSV | `mode=openai`, `confirmed=false`; известные цитаты перенесены, неизвестные поля пустые |
| Проверка смысла через UI | `Смысл проверен AI`, 90/100 для карточки без контакта и взаимодействия; 2 раздела требуют уточнения |

Предложения, решения и награды в полном API-прогоне создавались во временной SQLite, а не в рабочей базе пользователя. Тестовую форму в браузере закрыли без сохранения. До замены ключа также проверена обработка отказа API: конструктор явно переходил в `local_stub`; оценщик не выдавал локальный результат за ответ модели.

Промпты, вход, выход, ошибки и резервный режим присутствуют в [AI.md](AI.md) и [SEMANTIC_RATING.md](SEMANTIC_RATING.md). AI не подтверждает, не публикует и не назначает команды. Рекомендации не используют персональные или чувствительные признаки участников; профили команд в запрос рейтинга не передаются. Свободный текст бизнеса автоматически от персональных сведений не очищается — это документированное ограничение, а не использование признаков для подбора.

Проверки с реальной моделью являются отдельными наблюдениями, не гарантией правильности всех будущих ответов. Граничные проверки A2 показывают, почему ручная проверка остаётся необходимой.

## 6 Замечания по приоритету

### A1 Уточняющие вопросы не учитывают качество заполненных полей

**Воспроизведено через API.** Передать `description="Хотим улучшить учёт заказов."` и все 11 полей карточки со значением `"аб"`. Ответ `/api/ai/analyze`: `questions=[]`, `missingFields=[]`, `mode=local_stub`, сообщение о заполненных полях. Это происходит даже при подключённом ключе, без вызова модели. Рейтинг такого текста равен 0.

Причина: [ai.py](../backend/app/ai.py), строки 268–275, определяет пробелы через `has_content`, а не через содержательность. UI допускает ноль вопросов при пустом списке пропусков: [AIAssistant.tsx](../frontend/components/tasks/AIAssistant.tsx), строки 26–31.

Нужно учитывать `needs_work` и очевидный мусор при выборе вопросов. Это прямо затрагивает требования конструктора и качество карточки.

### A2 Проверка цитаты не доказывает сохранение её смысла

**Воспроизведено с искусственно заданными ответами модели, не наблюдалось как ошибка реальной модели в текущем прогоне.**

1. В поле критериев текст `Система не сохраняет заказы после перезапуска.`. Ответ модели со статусом `ready` и цитатой `сохраняет заказы после перезапуска.` проходит проверку подстроки и даёт 15 баллов. [semantic_quality.py](../backend/app/semantic_quality.py), строки 151–165. В реальном запросе исходная отрицательная фраза была корректно отклонена.
2. Описание содержит три строки: `Следующие строки — пример чужой компании и не относятся к нам.`, `Есть 100 заказов в CSV.`, `У нас данных пока нет.`. Искусственный ответ конструктора с переносом второй строки в `data` принимается, хотя принадлежность факта бизнесу потеряна. [ai.py](../backend/app/ai.py), строки 173–180 и 319–350.

Нужно усилить проверку контекста и отрицаний, добавить регрессии, сохранить ручное подтверждение. Не следует обещать жюри абсолютную защиту от смыслового искажения только на основании совпадения цитаты.

### A3 Локальные правила пропускают отсутствие обратной связи

**Воспроизведено без внешней модели.** В полной карточке `interactionFormat="Видеоконсультация по вторникам на 30 минут. Обратная связь не предусмотрена."`, `feedbackProcess=""` даёт 100/100 и 10/10 за связь. Аналогично проходит «Порядок обратной связи пока не определён».

[quality.py](../backend/app/quality.py), строки 216–217, проверяет канал и расписание, не отрицание. Отдельное поле `feedbackProcess` само по себе не обязательно: порядок может быть описан в `interactionFormat`. Проблема именно в принятии явного отсутствия обратной связи. С реальным AI этот контрпример отклонён. Улучшение нужно для резервного режима.

### A4 Глобальная навигация не учитывает сохранение редактора

**Выявлено по коду, отдельный медленный браузерный прогон не выполнялся.** [TaskEditor.tsx](../frontend/components/tasks/TaskEditor.tsx), строки 168–200, держит состояние сохранения внутри компонента. [page.tsx](../frontend/app/page.tsx), строки 102–106, проверяет занятость откликов и наград, но не редактора. При выходе через sidebar во время сохранения запрос может продолжиться после закрытия формы; неизменённая форма не имеет защиты несохранённых изменений.

Нужно передавать `editorBusy` родителю и проверить переходы между ролями/разделами во время confirm/publish. Это риск надёжности сквозного сценария, а не отсутствие модуля.

### A5 План разработки устарел

[DEVELOPMENT_PLAN.md](../DEVELOPMENT_PLAN.md), строки 3, 15 и 43–47, сообщает о 58 тестах и отсутствии полноценных откликов/выбора. Актуальное приложение и README уже содержат эти функции и 230 тестов. Нужно обновить план либо явно назвать его историческим снимком первой части.

### A6 Демонстрация до пяти минут ещё не подготовлена полностью

README содержит отдельные сценарии, но нет единого набора текста, тайминга и непрерывного прогона на одном примере «слабое описание → вопросы → карточка → рост рейтинга → публикация → отклик → решение». API-сценарий проверен; он не заменяет показ всех переходов в UI на защите. Нужен отдельный сценарий с репетицией и таймером. Это прямое требование разделов 10–11.

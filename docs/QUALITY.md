# Проверка качества описания задачи

Этот документ описывает локальные правила `rules-v2`, применяемые к предварительной оценке и при отсутствии ключа. При подключённом API подтверждение карточки использует [семантическую AI-проверку](SEMANTIC_RATING.md). Локальные правила не заменяют понимание смысла внешней моделью. Ответы из 1–3 букв, повтор одной буквы и наборы однобуквенных фрагментов отклоняются до начисления баллов.

Проверка в [quality.py](../backend/app/quality.py) оценивает конкретность описания до начисления баллов. Это локальные детерминированные правила `rules-v1`: они не вызывают модель, не требуют API-ключа и не меняют текст бизнеса. AI-конструктор остаётся отдельной функцией: его промпт, источники и резервный режим описаны в [AI.md](AI.md).

## Как меняется рейтинг

Для каждого оцениваемого поля выполняются три условия: есть содержательный текст, поле прошло проверку качества, бизнес подтвердил текущую версию и соответствующее поле. Только тогда начисляется полный вес поля. Частичных баллов за длину текста нет.

```text
R = Σ (вес поля × подтверждение × прохождение правил качества)
```

| Поле | Вес | Что ищет проверка |
| --- | ---: | --- |
| Контекст | 10 | Описание текущего процесса и конкретного предмета работы |
| Потребность | 10 | Требуемое изменение и предмет изменения |
| Данные и материалы | 20 | Источник/формат и сведения о составе материалов; явно отсутствующий или ещё не полученный источник не учитывается |
| Ожидаемый результат | 15 | Передаваемый артефакт и его функции или предмет |
| Критерии успеха | 15 | Наблюдаемый результат плюс измерение либо воспроизводимое условие теста |
| Ограничения | 10 | Конкретная граница: срок, бюджет, разрешённая технология, запрет или ограничение доступа |
| Пользователи | 10 | Распознаваемая группа пользователей с контекстом или ролью |
| Контакт | 5 | Email, международный телефон, Telegram-контакт или поддерживаемая прямая ссылка для связи |
| Консультации и обратная связь | 5 | Канал общения и время, периодичность встреч или срок ответа |

Название, компания, тема, навыки и дополнительное поле `feedbackProcess` отдельных баллов не дают. Уровни сохраняются: 0–39 — черновик, 40–69 — рабочая, 70–89 — готовая, 90–100 — приоритетная.

Перед подтверждением `previewRating` показывает потенциальные баллы, а `rating.score` неподтверждённой версии равен 0. Подтверждение человеком не отменяет замечания качества: если поле осталось неконкретным, за него по-прежнему 0 баллов. При этом публикация и отклик разрешены при любом рейтинге; для публикации нужны непустое название и ручное подтверждение.

## Проверяемые примеры

| Поле и ввод | Результат |
| --- | --- |
| Критерии: «Всё должно работать хорошо» | Нужно уточнить: нет измерения или воспроизводимой проверки |
| Критерии: «Компания работает с 2026 года и имеет 10 сотрудников» | Нужно уточнить: числа не описывают проверку решения |
| Критерии: «CSV содержит 100 строк» | Нужно уточнить: описан входной материал, но не результат работы |
| Критерии: «Импорт не работает, 100 строк» | Нужно уточнить: описан отказ функции, а не условие приёмки |
| Критерии: «100 строк импортируются без потерь; фильтр отвечает до 1 секунды» | Достаточно конкретно для 15 баллов после подтверждения |
| Критерии: «После перезапуска приложения сохранённые заказы отображаются в списке» | Достаточно конкретно: условие теста и ожидаемый результат, число не обязательно |
| Критерии: «При вводе неверного email форма отклоняет запись и показывает ошибку» | Достаточно конкретно: проверяемое отклонение некорректного ввода |
| Данные: «Доступ к CSV с заказами не предоставлен» | Нужно уточнить: источник пока недоступен |
| Данные: «Доступ к CSV с заказами не предоставлен. Есть 30 синтетических заказов в JSON с описанием полей» | Учитывается доступная альтернатива во втором предложении |
| Ограничения: «Только Python» | Достаточно конкретно: короткая формулировка может быть полезной |

Пустые поля и явные заглушки получают статус `missing`. Неконкретные формулировки, случайные наборы символов, преобладающее повторение слов/фраз и одинаковый текст в разных разделах получают `needs_work`. Повторение служебных слов и технических идентификаторов само по себе не является ошибкой. Например, формула с несколькими `stock_qty` и `shortage_qty` допустима.

## API и интерфейс

`POST /api/rating/preview` принимает `{"fields": TaskFields}` и возвращает оценку без записи в базу. В каждом `Rating` есть `quality`:

- `version`: версия набора правил, сейчас `rules-v2`;
- `mode`: `rules`;
- `fields`: девять результатов с ключом `field`, статусом `missing` / `needs_work` / `ready`, пояснением `message` и подсказкой `suggestion`;
- `eligibleFields`: поля, которые могут получить баллы после подтверждения;
- `summary`: краткий итог с явным обозначением эвристического характера проверки.

`Rating.missingFields` по-прежнему перечисляет только пустые поля или заглушки. Для заполненных, но недостаточно конкретных полей нужно читать `quality.fields`, а не считать отсутствие поля в `missingFields` признаком готовности. Подсказки также входят в `breakdown[].missing` соответствующего показателя.

Редактор показывает замечания у полей и в панели рейтинга. Пользователь сам исправляет текст. Проверка не добавляет требования, сроки, метрики или сведения о доступе от имени бизнеса. Затем человек подтверждает текущую версию и публикует её; до повторной публикации каталог использует предыдущий опубликованный снимок.

При первом запуске версии с новыми правилами сервер пересчитывает производные оценки сохранённых задач. Черновик и опубликованный снимок оцениваются независимо по своим собственным полям и подтверждениям. Тексты, ревизии и решения бизнеса не заменяются; изменения черновика не публикуются. Исходные файлы набора данных сохраняются без исправления. Версия расчёта записывается в `metadata.rating_version`; при последующих изменениях правил её нужно повышать.

## Границы проверки

Правила ориентированы на русские описания и распространённые технические термины. Они проверяют признаки конкретности, но не устанавливают истинность данных и не гарантируют смысловую корректность любого текста. Перефразирование, редкая терминология и противоречивые формулировки могут давать ложные срабатывания или пропуски. При спорной оценке интерфейс показывает причину, чтобы бизнес уточнил формулировку; скрытого автоматического редактирования или назначения команды нет.

Проверка не открывает ссылки, не исследует файлы CSV и не проверяет, существует ли указанный контакт. Достоверность и возможность передачи материалов подтверждает бизнес. Оценка не использует компанию, популярность, число откликов или персональные и чувствительные признаки участников.

## Проверка реализации

Из корня проекта:

```bash
backend/.venv/bin/python -m pytest backend/tests/test_quality.py backend/tests/test_demo_data.py -q
```

Регрессии проверяют измеримые и бинарные условия приёмки, числа без критерия, отрицания, отсутствие доступа, доступную альтернативу, короткие ограничения, повторяющиеся технические имена, бессмысленные повторы, сохранение исходного текста и обязательность подтверждения. Проверяется демонстрационный рост оценки **20 → 55 → 70** и исходные карточки **20 / 50 / 75 / 90 / 100**. Общий сквозной сценарий качества, отклика и ручного выбора команды находится в [test_workflow.py](../backend/tests/test_workflow.py).

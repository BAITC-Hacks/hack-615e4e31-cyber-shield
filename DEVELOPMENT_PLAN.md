# План разработки MVP HackAlem

Статус: подготовлен план и распределение задач. Разработка приложения не начата.

Цель: за рабочую сессию собрать демонстрируемый путь от слабого описания бизнес-задачи до публикации, отклика команды и ручного решения бизнеса. Ориентир из кейса — пять часов; приведённое расписание является бюджетом времени, а не обещанием срока.

## Команда

Пользователь принимает продуктовые решения, проверяет удобство и готовит защиту. Ему не требуется самостоятельно координировать агентов или переносить между ними сообщения.

Координатор Codex определяет общие контракты, создаёт основу приложения, соединяет модули, проверяет весь сценарий и готовит запуск. В текущей сессии доступны три дополнительных одновременно работающих агента.

| Исполнитель | Задачи при разработке | Результат и критерий готовности |
| --- | --- | --- |
| Агент интерфейса | Конструктор описания, редактирование карточки, панель рейтинга, каталог, форма отклика, список предложений бизнеса | Все шаги доступны из интерфейса; есть загрузка, ошибка и пустое состояние; рейтинг приходит из общей логики |
| Агент бизнес-логики | Формула рейтинга, подтверждение полей, правила публикации и откликов, синтетические данные | Одинаковые данные дают одинаковый балл; низкий рейтинг не мешает отклику; допускается ручной выбор нескольких команд |
| Агент AI-помощника | Уточняющие вопросы, сборка карточки, промпт, проверка ответа, адаптер API и резервный режим | Не менее трёх уместных вопросов; неизвестные сведения остаются пустыми; сбой API не уничтожает ввод |
| Координатор | Каркас, общие типы, состояние и хранение, интеграция, запуск, проверки в браузере, README и сценарий защиты | Весь путь работает в одной сборке и воспроизводится после запуска по инструкции |

При подготовке этого плана агенты выполнили независимый анализ требований, интерфейса и архитектуры. Код они не изменяли.

## Обязательный объём

1. Переключение демонстрационных ролей «Бизнес» и «Команда».
2. Свободное описание задачи, минимум три уточняющих вопроса и ответы.
3. Редактируемая карточка: название, контекст, потребность, пользователи, данные, ограничения, ожидаемый результат, критерии успеха, контакт и формат взаимодействия. Формат взаимодействия явно включает порядок обратной связи.
4. Рейтинг 0–100 с объяснением, списком недостающего и пересчётом после подтверждения.
5. Публикация в общем каталоге, сортировка по рейтингу и фильтры по теме и готовности.
6. Отклик команды с идеей, планом, сроком и ссылкой на прототип.
7. Ручное принятие или отклонение предложений бизнесом. Можно выбрать одну, несколько или ни одной команды.
8. Не менее пяти черновиков, пяти карточек, пяти профилей команд и пяти откликов в тестовом наборе.
9. README с запуском, архитектурой, формулой, правилами каталога, AI-контрактом и тестовыми сценариями.

Регистрация, чат, уведомления, календарь, загрузка файлов, собственная ML-модель и полный трекер проектов в первый объём не входят. Рекомендации задач по навыкам — только после завершения обязательного пути.

## Работа без конфликтов

До распараллеливания координатор фиксирует схему данных, имена операций и демонстрационный пример. Затем агенты получают отдельные области файлов и проверяемый результат.

Предлагаемые границы при выборе TypeScript:

- Общие типы и схемы, точка входа, маршрутизация, хранение, конфигурация и зависимости — координатор.
- Компоненты экранов и стили интерфейса — агент интерфейса.
- `src/domain/`, `src/fixtures/` и проверки бизнес-правил — агент бизнес-логики.
- `src/ai/` и согласованный серверный маршрут AI — агент AI-помощника.

Это будущая структура, а не уже созданные файлы. Конкретный стек выбирается перед реализацией с учётом способа запуска.

Агенты не изменяют общие контракты и зависимости самостоятельно. Изменение границы согласуется через координатора. После реализации выполняется взаимная проверка: агент проверяет модуль, который писал другой агент. Финальную интеграцию и проверку пользовательского пути выполняет координатор.

## Документация запуска

Явное требование пользователя: проект должен сопровождаться понятной инструкцией запуска. README создаётся вместе с первым работающим каркасом и обновляется при изменении команд, зависимостей или настроек. Итоговую документацию ведёт координатор; каждый агент при сдаче модуля сообщает его зависимости, настройки и способ проверки.

README на русском языке должен содержать:

1. Требования к окружению и проверенные версии инструментов для выбранного стека.
2. Получение исходников, установку зависимостей и подготовку окружения с точными командами и указанием рабочей папки.
3. Настройку переменных окружения по `.env.example`: назначение каждой переменной, обязательность и безопасные примеры без секретов.
4. Подготовку базы, загрузку демонстрационных данных и отдельную явно обозначенную команду их сброса.
5. Запуск интерфейса и сервера, порядок команд, число терминалов, адрес приложения и признак успешного запуска.
6. Работающий демонстрационный режим без AI-ключа и отдельную инструкцию подключения реального AI.
7. Остановку и повторный запуск, а также пояснение, какие данные сохраняются.
8. Команды проверок и сборки, краткий сценарий демонстрации и решения типичных проблем: занят порт, отсутствует настройка, недоступны API или база.
9. Поддерживаемые и фактически проверенные операционные системы. Различающиеся команды описываются отдельно; непроверенная совместимость не заявляется как подтверждённая.

При выборе размещения по ссылке добавляется инструкция развёртывания и настройки постоянного хранения. Команды в README должны соответствовать реальным скриптам проекта; пока реализации нет, команды запуска не выдумываются.

Перед сдачей выполняется проверка по README в чистой копии проекта с заново установленными зависимостями и новой тестовой базой. Проверяющий агент следует только инструкции, а найденные пропущенные шаги исправляются в документации. В README фиксируются проверенное окружение и ограничения проверки.

## Общие контракты

Основные сущности: задача, поля карточки, уточняющий вопрос, ответ, результат рейтинга, профиль команды, отклик. Тема каталога хранится отдельно от описания задачи.

Основные операции:

- Анализировать черновик и получить вопросы.
- Предложить поля карточки по исходному тексту и ответам.
- Сохранить изменения и подтвердить карточку.
- Рассчитать рейтинг с разбивкой по критериям.
- Опубликовать подтверждённую версию.
- Получить каталог с сортировкой и фильтрами.
- Отправить отклик и вручную изменить его статус.

У публикации и готовности разные состояния. Неопубликованный черновик не попадает в каталог. Опубликованная карточка с оценкой ниже 40 остаётся видимой и принимает отклики. При последующих правках каталог использует последнюю подтверждённую опубликованную версию.

Принятие одного отклика не отклоняет остальные автоматически. Выбор команды всегда выполняет бизнес.

## Рейтинг

Берём рекомендованные веса кейса: контекст и потребность — 20, данные — 20, результат — 15, критерии успеха — 15, ограничения — 10, пользователи — 10, связь с бизнесом — 10.

Расчёт выполняет обычная функция по опубликованным правилам. ИИ помогает выявить пробелы, но не назначает итоговый балл. За пустые и неподтверждённые сведения баллы не начисляются.

До реализации нужно определить условия полного и частичного зачёта каждого критерия. Проверки наличия и структуры сведений воспроизводимы; достоверность утверждений бизнеса и фактическую доступность данных они не гарантируют. Рейтинг нельзя представлять как автоматическую проверку истинности.

Полные 10 баллов за связь с бизнесом требуют контакта, формата консультаций и порядка обратной связи. До передачи модуля агентам фиксируем правила частичных баллов и снятия подтверждения после редактирования. На демонстрации изменение оценки объясняется конкретными подтверждёнными сведениями и соответствующими строками разбивки.

Проверяем уровни 0–39, 40–69, 70–89 и 90–100, соответствие суммы разбивке и повторяемость расчёта.

## AI-помощник

AI-функция внутри продукта и агенты-разработчики — разные части работы. Для реального AI в приложении потребуется доступ к выбранному сервису. Вызов с секретным ключом выполняется на сервере.

Раздел 5 кейса — обязательное требование пользователя. Основной сценарий предусматривает содержательную AI-функцию: модель анализирует полноту конкретного описания и формирует минимум три уместных уточняющих вопроса по обнаруженным пробелам. Дополнительно модель предлагает структуру карточки по полученным ответам. Вопросы должны учитывать уже сообщённые сведения; один и тот же фиксированный список для всех описаний не выдаётся за работу модели.

Контракт AI фиксируется до разработки интерфейса:

- Вход: операция уточнения или сборки, исходный текст, ответы, текущая карточка.
- Выход: версия формата, режим работы, вопросы с привязкой к полям, предложенные значения с фрагментами-основаниями из ввода, недостающие сведения и предупреждения.
- Для операции уточнения возвращаются минимум три вопроса.
- Неизвестные значения возвращаются как `null`; в интерфейсе они отмечаются как неуказанные. Предложения не считаются подтверждёнными.
- Ответ не содержит решений о публикации, выборе команд или начислении баллов.

Ограничения и их реализация:

1. Модель не должна придумывать факты, сроки, числовые цели, пользователей или источники данных. Предложенное значение связывается с сообщёнными сведениями; отсутствие основания означает пробел или уточняющий вопрос. Проверка структуры JSON и наличия исходных фрагментов не доказывает смысловую корректность: нужны содержательные проверки на примерах и просмотр человеком.
2. Результат AI показывается как редактируемый черновик. Сервер не разрешает публикацию новой версии без явного подтверждения её человеком. Повторная генерация и правки снимают подтверждение изменённых сведений.
3. AI не получает операций выбора или назначения команды. Принятие и отклонение отклика выполняет бизнес через обычные действия приложения; текст ответа модели не запускает эти действия.
4. Рекомендации по интересам и навыкам остаются необязательным расширением. Если они появятся, общий каталог сохранит все опубликованные задачи и возможность откликнуться независимо от рекомендаций.
5. Персональные и чувствительные признаки участников не используются при анализе или рекомендациях. Профиль для возможных рекомендаций содержит только интересы, навыки и технологии. Контакт бизнеса хранится отдельно от данных для AI; для оценки заполненности контакта достаточно проверки его наличия обычной логикой. В демонстрации используются синтетические данные. Перед отправкой свободного текста должна быть предусмотрена проверка и удаление обнаруженных персональных сведений; автоматическая проверка не представляется как гарантия обнаружения всех таких сведений.

При отсутствии API, тайм-ауте или некорректном ответе включается явно обозначенный резервный режим с тем же контрактом. Он использует вопросы по незаполненным полям и переносит ответы без выдумывания сведений. Кейс допускает такую заглушку при недоступности API, если показаны промпт, вход, выход и обработка ошибки. Заглушка не выдаётся за живую генерацию.

Документация AI-модуля входит в сдачу: точный используемый промпт, схема входа и выхода, пример успешного запроса, пример неверного ответа и описание реакции приложения. README ссылается на эти материалы и объясняет различие основного и резервного режимов. Агент AI-помощника готовит материалы своего модуля, координатор сверяет их с реализацией.

Проверки AI-модуля:

- На двух черновиках с разными пробелами получаются вопросы по соответствующим отсутствующим сведениям, не менее трёх в каждом сценарии уточнения.
- Ввод без срока, бюджета, целевой метрики и источника данных не превращается в карточку с выдуманными значениями этих полей.
- Невалидный JSON, неверные типы, неизвестные поля или недостаточное число вопросов не принимаются как успешный ответ. Ввод сохраняется, пользователю сообщается об ошибке или резервном режиме.
- Сбой или недоступность API сохраняют возможность завершить демонстрацию в обозначенном резервном режиме.
- Попытка публикации без подтверждения блокируется на сервере; подтверждение относится к текущей версии карточки.
- Выбор команд возможен только ручным действием бизнеса. Рекомендации, если добавлены, не меняют доступность задач и откликов.
- Состав AI-запроса проверяется: он не включает контакты и персональные или чувствительные признаки участников; обработка свободного текста проверяется на синтетических примерах.

## Критерии оценки и доказательства готовности

Источник весов — раздел 9 кейса. Максимальная оценка проекта составляет 100 баллов. Это отдельная шкала от рейтинга готовности бизнес-задачи 0–100 внутри приложения: в интерфейсе и документации эти значения не смешиваются.

| Критерий | Баллы | Что реализуем и проверяем | Что показываем жюри | Ответственный |

| Сквозной сценарий | 20 | Одна созданная пользователем задача проходит все операции с сохранением данных | Черновик → уточнение → подтверждённая карточка → публикация → новый отклик → ручное решение бизнеса в работающем приложении | Координатор; все агенты исправляют свои модули |

| AI-функция | 10 | Полезные вопросы или структурированная карточка по вводу без добавления фактов; валидация ответа и предусмотренный резервный режим | Результат на реальном вводе; связь с исходными сведениями; промпт, схема и пример обработки ошибки доступны в документации | Агент AI-помощника; координатор проверяет интеграцию |
| Техническое качество | 10 | Воспроизводимый запуск, валидация, понятная структура, README и тестовые данные | Запущенное приложение, краткая схема архитектуры, инструкция и результат проверки запуска в чистой копии | Координатор; агенты документируют свои модули |
| Демонстрация | 5 | Один подготовленный пример, весь сценарий до пяти минут, воспроизводимый сброс демонстрационных данных | Непрерывный проход по работающему MVP; переходы не подменены слайдами или вручную изменённой базой | Пользователь и координатор |

Порядок разработки учитывает веса: сквозной сценарий, карточка и геймификация вместе составляют 60 баллов. Сначала обеспечиваем основу этого сценария, затем завершаем все остальные обязательные критерии. Небольшой вес критерия не делает соответствующее обязательное требование необязательным.

При сдаче каждого модуля агент указывает связанные критерии, способ воспроизвести результат, выполненные проверки и известные ограничения. Координатор считает критерий покрытым только после проверки общей сборки; завершение отдельных файлов недостаточно.

Для проверки влияния рейтинга используем задачи с разными вычисленными оценками. Подтверждаем, что улучшение опубликованной задачи и публикация новой версии действительно меняют её место относительно других задач. Баллы и позиции не задаются вручную ради демонстрации.

Сценарий защиты составляется под матрицу: ввод и вопросы, редактирование и рост рейтинга, публикация и каталог, отклик и решение бизнеса. Технические детали и ограничения объясняются кратко; проверка с таймером проводится до сдачи.

## Бюджет пяти часов

| Время | Совместный результат |
| --- | --- |
| 0–25 минут | Выбраны способ запуска и хранения; зафиксированы схема данных, контракт AI и границы файлов; создан каркас |
| 25–110 минут | Параллельно создаются интерфейс, бизнес-логика и AI-модуль; координатор соединяет первый путь на тестовых данных и пишет первоначальную инструкцию запуска |
| 110–180 минут | Работают уточнение, карточка, рейтинг, каталог, отклик и решение бизнеса; подключается реальный AI при наличии доступа |
| 180–230 минут | Проверены основные правила, сохранение данных и сбои; исправлены ошибки интеграции |
| 230–270 минут | Завершены оформление, README, тестовый набор и сценарий защиты |
| 270–300 минут | Проведён полный прогон демонстрации; проверен запуск; исправляются только блокирующие проблемы |

Интеграция начинается в первой фазе разработки. Не откладываем первое соединение модулей до конца хакатона.

## Приёмка MVP

1. Слабое описание проходит через вопросы, редактирование, подтверждение, публикацию, отклик и ручное принятие.
2. Подтверждённое дополнение меняет рейтинг и при необходимости позицию в каталоге; неподтверждённая правка не меняет опубликованную версию.
3. Задача с рейтингом ниже 40 видна в каталоге и доступна для отклика.
4. Бизнес может выбрать несколько команд, отклонить предложения либо никого не выбрать.
5. Показана содержательная AI-функция либо, при недоступности API, явно обозначенная заглушка. Проверены ограничения и сценарии AI-модуля; доступны точный промпт, формат входа и выхода и пример обработки некорректного ответа. Введённые данные при ошибке сохраняются.
6. Данные переживают перезагрузку в рамках согласованного режима хранения.
7. Приложение запускается в чистой копии по README без неописанных действий; проверены подготовка базы, тестовые данные и режим без AI-ключа. Демонстрация укладывается в пять минут.

## Что решаем перед реализацией

- Способ показа: локальная демонстрация или доступ по ссылке с нескольких устройств. Для общего состояния разных пользователей требуется серверное хранение.
- Доступ к AI-сервису и способ безопасного подключения. Отсутствие доступа не блокирует остальные модули.
- Баллы студентам за этап: в сценарии кейса они есть, но в обязательных модулях и демонстрации не раскрыты. По возможности уточнить у организаторов; при необходимости добавить одно ручное подтверждение этапа без полноценного трекера.

## Регулярное сохранение в GitHub

Репозиторий: https://github.com/BAITC-Hacks/hack-615e4e31-cyber-shield.git. Рабочая ветка: `main`.

Пользователь явно запросил первый commit и push текущих материалов сразу и последующее сохранение новых изменений каждые 40 минут. Под деплоем в этом запросе понимаются только commit и push в GitHub. Развёртывание сайта не входит в эту автоматизацию.

В текущей задаче Codex создана активная автоматизация `github-40`. Она проверяет состояние проекта, сохраняет целостный промежуточный снимок кода и документации и отправляет коммиты в `origin/main`. При отсутствии изменений и неотправленных коммитов новый коммит не создаётся. Незавершённые части и известные проблемы отмечаются в описании промежуточного коммита.

Координатор согласует снимок с работающими агентами, проверяет состав изменений и исключает секреты, зависимости, локальные данные и сборочные артефакты. Удалённая история сохраняется; force push не используется. Ошибка доступа или конфликт сообщаются пользователю. Автоматизация сохраняет уже сделанное и сама по себе не запускает разработку новых функций.

Расписание выполняется локально через Codex, поэтому компьютер должен быть включён, приложение запущено и доступ к GitHub сохранён. Уведомления выдаются об отправке новых изменений или новой проблеме; неизменившееся состояние не порождает повторные сообщения.
